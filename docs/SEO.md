# SEO и ИИ-поиск: как сделать репозиторий находимым

Цель: чтобы человек, который ищет «Haval M6 не видит фильм», «AVI XviD
Haval M6», «M6 не воспроизводит MKV», «флешка exFAT Haval», попадал на
этот репозиторий и сразу получал ответ и инструмент.

## 1. Метаданные GitHub

Заполняются в **About** репозитория, а не в README. Это главный сигнал для
поиска GitHub и описаний в выдаче.

Описание (до 350 символов), русский вариант:

> Haval M6 (2023/M6 Plus): почему не воспроизводятся AVI/XviD, AC3 и
> некоторые MKV. Скрипт находит несовместимые файлы, конвертирует только
> их в H.264/AAC MP4, готовит музыку и фото, разбивает файлы под FAT32.

Английский вариант:

> Fix Haval M6 (2023) USB playback: convert AVI/XviD, AC3 and unsupported
> MKV files to H.264/AAC MP4. Prepares music/photos, handles FAT32 and
> exFAT, writes a JSON report.

## 2. README как посадочная страница

Человек и поисковый сниппет читают первые 5–10 строк. Сейчас в README есть
ответ, но его можно усилить:

* заголовок содержит «Haval M6», «AVI/XviD», «AC3», «USB»;
* первый абзац отвечает на конкретный запрос, а не описывает проект;
* есть раздел «Частые проблемы» и ссылки на FAQ и матрицу совместимости;
* есть английская версия для запросов на английском.

Не надо вставлять список ключевых слов в подвал — поиск это игнорирует, а
люди уходят. Важнее совпадение **заголовков с формулировкой проблемы**:
«не видит», «не воспроизводит», «нет звука», «больше 4 ГБ», «exFAT».

системы — страницы репозитория. Чем точнее заголовки, тем выше шанс
попасть в ответ.

## 4. ИИ-поиск (ChatGPT, Claude, Perplexity, Copilot и т. п.)

Агенты и LLM-краулеры читают:

* [llms.txt](../llms.txt) — короткий индекс и ответы;
* [AGENTS.md](../AGENTS.md) — инварианты и команды;
* [schema/manifest.schema.json](../schema/manifest.schema.json) — формат
  отчёта;
* [docs/ARCHITECTURE.md](ARCHITECTURE.md) — как работает конвейер.

Что важно для ИИ-ответов:

1. Явно писать **вопрос → короткий ответ → команда** в FAQ.
2. Не прятать ответ в длинном тексте.
3. Держать `llms.txt` в актуальном состоянии.
4. Давать точные имена действий (`copy-video`, `transcode`) и exit codes.
5. Не добавлять вымышленные форматы и «гарантии»; писать «обычно»,
   «на практике», «проверено на прошивке».

## 5. Релизы и история

* Создать GitHub Releases для тегов (`v1.2.0`).
* В описании релиза — 3–5 строк: что исправлено и какие команды.
* Вести `CHANGELOG.md` (можно начать с 1.2.0).
* Не переписывать опубликованные теги; версии должны быть стабильны.

## 6. Ссылки и сообщества (без спама)

Один хороший ответ с ссылкой полезнее сотни комментариев. Где искать
аудиторию:

* форумы Haval M6 / Haval-clubs;
* Drive2 и профильные статьи;
* Reddit-сообщества про Haval и car media;
* YouTube-комментарии под обзорами M6 (по делу, без навязывания);
* ответы на Stack Overflow / Super User, если вопрос реально про ffmpeg.

Правило: сначала ответить по существу, потом дать ссылку на инструмент.
Не вставлять ссылку в каждый пост.

## 7. Социальный preview и оформление

* Загрузить social preview 1280×640: скриншот терминала + надпись
  «Haval M6: AVI/XviD → H.264/AAC».
* В README — один скриншот/схема, не десять.
* Проверить, что репозиторий открывается без логина и что README
  рендерится на мобильном.

## 8. Что не делать

* Не добавлять «1000 ключевых слов» и не перечислять названия фильмов.
* Не обещать поддержку форматов, которых нет в инструкции/проверке.
* Не публиковать личные пути, email и названия релизов.
* Не создавать десятки пустых репозиториев-клонов под запросы.
* Не покупать «SEO-тексты»; проект должен отвечать на вопрос.
